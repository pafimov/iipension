# Эксплуатация и публикация

## Локальный стенд

Compose — воспроизводимый **локальный** запуск, не production deployment. Web доступен только loopback, PostgreSQL и API внутри сети Compose. `make up` ждёт БД, выполняет миграции отдельным одноразовым сервисом, затем запускает API и web. Health probes различают живой процесс и доступную таблицу.

При пересоздании backend image отдельно пересоздайте migration job, чтобы новая миграция не была пропущена: `docker compose up --build --force-recreate migrate`, затем `docker compose up --build --wait`. Это простой локальный rollout с возможной паузой, не обещание бесшовного обновления.

## Перед доступом внешних пользователей

Выберите VPS/PaaS/контейнерный хостинг. Отдельно настройте DNS и TLS ingress; публично публикуется только HTTPS origin. Выберите базу/backup policy и secret store платформы.

1. `APP_ENV=production`, уникальный DJANGO_SECRET_KEY >=50 символов, сильный DB password, точные ALLOWED_HOSTS и CSRF_TRUSTED_ORIGINS=https://ваш-домен. Никогда не оставлять local-флаг в public deployment. PostgreSQL наружу не публиковать.
2. Текущий Nginx-конфиг обслуживает локальный HTTP. Для HTTPS ingress адаптировать proxy-конфигурацию так, чтобы доверенный ingress **перезаписывал** X-Forwarded-Proto, backend недоступен напрямую. Только после этого выставить `TRUST_HTTPS_PROXY=1`. Иначе перенаправления/cookies будут работать неверно или появится доверие чужому заголовку.
3. Для внешней БД включить `POSTGRES_SSLMODE=verify-full` и доверенный CA; настроить сетевые правила. Не отключать проверку TLS.
4. Добавить ingress rate limit на auth и общие запросы, корректную доверенную proxy-IP цепочку и лимиты ресурсов. Axes уже блокирует пару username+peerIP после 5 неуспехов на час; его таблицы требуют retention. `manage.py axes_reset` — административное снятие блокировок. Просроченные сессии чистить `clearsessions` по расписанию.
5. Создавать пользователей административно. Для самостоятельного публичного signup сначала реализовать верификацию адреса, восстановление, abuse protection и выбранный провайдер/MFA. Не открывать административную ручку всем.
6. `python manage.py check --deploy` в production окружении, миграции на копии БД, `make check`, PostgreSQL и browser smoke. Не ослаблять проверки ради выкладки.
7. Определить owner поддержки, retention/удаление личных данных, error monitoring, alert по 5xx/readiness, HTTPS renewal. В логах/телеметрии исключить тела запросов, cookies, пароли и финансовые поля.

## Миграции, релиз и откат

Собирать immutable image с commit SHA и lock-файлами. Сначала резервная копия и проверенная совместимая миграция отдельной job, затем новый backend, readiness, web и browser smoke. Изменения БД по expand→migrate→contract, удаление колонок не совмещать с первым релизом нового кода. Миграции не запускать из каждого gunicorn worker.

Откат приложения — предыдущий image, только если схема совместима. Автоматический reverse data migration не гарантирует восстановление удалённых данных. Деструктивная миграция требует отдельного согласования и проверенного восстановления backup.

## Резервное копирование

Для managed PostgreSQL использовать штатные backups/PITR; для своей БД `pg_dump` в зашифрованное хранилище вне репозитория. Установить RPO/RTO под реальные требования и регулярно восстановить копию в отдельный инстанс. Проверить goal ownership и сессии после восстановления; при компрометации ротировать секреты и инвалидировать сессии.

Автоматический CD в шаблоне сознательно не привязан к провайдеру. Protected environments и доступ к deployment secrets настраиваются после выбора хостинга; pull requests от forks не должны получать их.
