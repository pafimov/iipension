# Практический цикл работы с агентом

## Первый промпт

> Прочитай AGENTS.md, docs/architecture.md, docs/product/traceability.md и scoped AGENTS. Возьми следующую задачу из docs/product/backlog.md. Сначала сверь FR/AC и неизвестные допущения. Реализуй одну законченную часть, обнови контракт/тесты/трассировку/worklog, выполни make check и релевантные проверки, сделай Conventional Commit. Не публикуй и не деплой без поручения. Не выдумывай недостающие финансовые правила. В конце дай результат, проверки, commit и ограничения.

В новом чате давать этот короткий промпт и конкретную задачу, а не всю историю проекта. Продолжение начинается с worklog и git status. Если есть отдельный дизайн/макет — указать точный файл и версию.

## Карточка задачи

```text
Цель: наблюдаемое поведение пользователя
Требования: FR-x, AC-FR-x.y
Входы/допущения: подтверждённые источники и открытые вопросы
Область: конкретные каталоги; что нельзя затрагивать
Готово, когда: конкретные сценарии и крайние случаи
Проверки: make check + DB/e2e по изменению
Результат: code + tests + docs/worklog + commit
```

## Агентная команда без лишних расходов

Один ведущий держит архитектуру, diff и финальные проверки. Один недорогой исполнитель делает ограниченную функцию/тесты; ещё один независимый ревьюер нужен только для денег, auth и миграций. Для чтения документации передавать ID требований и небольшой фрагмент, не все документы. Перед запуском проверить доступность модели; фактические тарифы зависят от провайдера, их нельзя вывести из имени модели.

Не запускать трёх агентов на одинаковое исследование. Параллельные задачи должны владеть разными файлами. Ведущий делает коммиты/merge, агенты возвращают список файлов и команды проверок. При quota error не обходить лимит сменой модели. При небольшом патче делегирование может стоить больше, чем самостоятельная правка.

## Критерий готовности

Поведение соответствует конкретным AC; ошибки не скрыты; owner/CSRF соблюдены; деньги точные; миграция и контракт синхронны; нет секретов/закрытых зависимостей; CI зелёный; UI проверен в браузере если менялся; worklog, трассировка и commit актуальны. Не пытаться получить большой процент coverage тестами, которые зеркалят код. Проверять независимые примеры и реальные отказы.

Локальные хуки не могут запретить ручной merge на хостинге. Нужны обязательные status checks и branch protection. Автоматический merge, squash, approval и deploy — настройки конкретного репозитория, см. repository-setup.md.
